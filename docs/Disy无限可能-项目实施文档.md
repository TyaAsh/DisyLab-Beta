## 2. 当前产品定位

### 2.1 品牌

- 品牌名：Disy 无限可能
- 产品形态：面向个人创作者的 AI 无限画布工作台
- 主要用户：个人设计师、电商视觉工作者、商品运营和内容创作者
- 核心价值：把提示词、参考图、生成结果和后续创作步骤放在一张可持续编辑的画布上

### 2.2 视觉方向

视觉方向参考 TapNow 一类 AI 创作平台的产品气质：

- 工作台优先，而不是传统后台管理系统。
- 卡片、圆角、轻量阴影和明显的操作反馈。
- 生成结果是视觉中心，参数面板保持克制。
- 默认提供深色和浅色两套主题。
- 深色主题保留科技感，但不照搬参考平台的 Logo、文案、图标或具体页面。
- 浅色主题保证长时间使用时的可读性，避免纯白大面积刺眼。

在此基础上加入苹果产品常见的拟态和材质表达，具体采用“克制的玻璃拟态 + 柔和层次”，而不是让所有组件都变成半透明玻璃：

- 面板使用半透明背景、背景模糊、细边框和柔和阴影表现层级。
- 关键操作使用清晰的实体按钮，避免透明按钮在复杂画布背景上失去可读性。
- 卡片、弹窗和节点保持较大的圆角，但节点之间仍然要有明确的选中边界。
- 深色模式使用低亮度背景、柔和高光和少量彩色光晕。
- 浅色模式使用暖白、浅灰和轻微材质阴影，避免高对比黑白界面。
- 动效强调响应感、空间感和状态变化，不使用持续晃动、过度弹跳或影响工作效率的装饰动画。

视觉关键词暂定为：

```text
AI 创作工作台 + TapNow 式内容生产感 + Apple 式材质层次 + 无限画布空间感
```

### 2.4 动效原则

参考项目已经使用 `Framer Motion`、`motion` 和 `GSAP`。Disy 会将它们纳入技术栈，但按职责分工使用：

| 动效库 | Disy 中的主要用途 | 不负责的内容 |
|---|---|---|
| Framer Motion | React 组件进入/退出、弹窗、面板、按钮反馈、主题切换 | 大量画布节点的持续帧动画 |
| Motion | 轻量 UI 状态过渡、布局变化、列表和卡片动效 | 复杂时间轴和高频画布动画 |
| GSAP | 画布级动效、连线流光、生成状态时间线、复杂序列和可控缓动 | 普通按钮和简单弹窗 |

第一版的动效优先级：

1. 节点创建、选中、连接和删除有明确反馈。
2. 生成任务有排队、进行中、成功和失败的连续状态。
3. 连接线可以表现数据流动，但不能影响拖拽和缩放性能。
4. 面板和弹窗打开关闭自然，支持减少动态效果设置。
5. 尊重系统 `prefers-reduced-motion`，用户关闭动效后保留状态变化但减少位移和连续动画。

动效实现规则：

- 画布节点移动优先使用 transform，不用频繁修改布局属性。
- 不在每个节点中各自创建独立的无限循环动画。
- GSAP 时间线必须可销毁，组件卸载时清理动画和事件监听。
- 生成中的流光、脉冲和进度效果必须与任务状态绑定，任务结束后停止。
- 动效不能替代错误提示、按钮文字、加载状态或可访问性标签。

三张用户提供的角色图作为第一版图生图测试素材和产品演示素材，分别用于：

- 角色外观保持测试。
- 场景和动作变化测试。
- 服装、道具和风格变化测试。

这些图片只作为本项目的测试输入，不默认写入代码仓库或公开发布页面；正式上线前需要确认素材版权和商业使用范围。

### 2.3 第一版生成能力

第一版只实现两种核心模式：

1. 文生图：用户输入提示词和参数，生成图片。
2. 图生图：用户上传或引用一张参考图，再输入提示词和参数，生成图片。

视频生成暂时不进入第一版开发，但节点模型和任务模型会预留媒体类型扩展，不在第一版中提前实现视频分支。

## 3. API 和商业模式边界

### 3.1 API 接入原则

用户要求参考项目的 API 接入方式。我们会保持等价的能力边界：

- Provider 和 Model 分离。
- 模型参数配置化。
- 统一的生成任务入口。
- Provider Adapter 负责请求、轮询、取消、结果解析和错误分类。
- 图片生成支持文本输入和参考图输入。
- API 端点支持用户配置的中转地址或兼容接口。

这里的“参考照做”指技术能力和调用协议的独立重实现，不复制参考仓库的源代码、私有实现、界面资源或品牌。

### 3.2 第一阶段的两种 API 使用方式

第一版不登录，因此先支持“自带 API Key（BYOK）”：

- Key 只保存在当前浏览器的本地安全存储中。
- Key 不写入画布节点、导出项目、日志或生成历史。
- 用户清空本地数据后，需要重新配置 Key。
- 这是适合个人试用的方式，不适合作为平台额度售卖的最终形态。

未来的“购买额度”模式需要登录和服务端账户体系：

- 用户登录后购买积分或订阅。
- 平台服务端持有平台 API Key。
- 前端不能看到平台 Key。
- 生成前检查余额，生成成功后扣费，失败按规则退款或不扣费。
- 订单、余额、任务和资产都绑定用户账号。

因此，当前产品路线是：

```text
无登录 + 自带 Key 的可用原型
→ 账号体系
→ 平台额度和支付
→ 面向公众售卖
```

## 5. 产品第一版应该做什么

第一版不追求参考项目的全部能力，而是先做一个可以真正使用、可以展示、可以继续售卖的 Web MVP。

### 3.1 第一版用户故事

用户打开网站后可以：

- 配置自己的 API Key；第一版不要求注册或登录。
- 创建、重命名、删除和切换项目。
- 在无限画布上缩放、平移、框选、拖拽和删除节点。
- 通过右键菜单创建文本、图片、视频、音频和上传节点。
- 编辑节点内容和生成参数。
- 将节点连接起来，形成简单的内容生产链路。
- 使用用户配置的 API 生成图片。
- 上传参考图并执行图生图。
- 查看生成中、成功、失败和重试状态。
- 将生成结果留在节点中，并保存到项目资产库。
- 刷新页面后恢复项目和画布。
- 导出项目 JSON，至少可以导入回本平台。

### 3.2 第一版暂时不做

以下能力先不进入 MVP：

- Tauri 桌面端和 Rust。
- 本地 ONNX 模型。
- ComfyUI、本地工作流和 Dreamina 登录态。
- 3D 导演台、全景、分镜、逐帧动画。
- 复杂的多 Agent、自主修改画布和项目记忆。
- 团队实时协作。
- 移动端专用编辑体验。
- 自建模型训练和模型托管。

这些不是永久取消，而是等画布核心和商业闭环验证后再加入。

## 6. 推荐的独立 Web 项目结构

第一阶段建议采用一个前端项目加一个轻量 API 服务。前端继续沿用参考项目最有价值的技术路线；服务端是商业化 Web 产品必须补上的部分。

```text
my-infinite-canvas/
├── apps/
│   ├── web/                         # React + Vite 前端
│   │   └── src/
│   │       ├── components/
│   │       │   ├── canvas/           # 画布、工具栏、右键菜单、连线
│   │       │   ├── nodes/            # 文本、图片、视频、音频、上传节点
│   │       │   ├── panels/           # 项目、资产、设置、任务面板
│   │       │   └── shared/           # 通用按钮、弹窗、状态组件
│   │       ├── hooks/                # 画布交互、自动保存、快捷键
│   │       ├── services/
│   │       │   ├── api/              # 调用业务服务端
│   │       │   ├── generation/       # 生成任务前端状态
│   │       │   └── storage/          # IndexedDB 缓存和离线草稿
│   │       ├── store/                # Zustand slices
│   │       ├── types/                # 节点、项目、任务和模型类型
│   │       └── App.tsx
│   └── api/                         # TypeScript API 服务
│       └── src/
│           ├── routes/               # 认证、项目、生成、资产、计费接口
│           ├── services/             # 任务、模型、存储、计费服务
│           ├── providers/            # 不同厂商 API 适配器
│           ├── workers/              # 异步生成任务
│           └── db/                   # 数据库 schema 和迁移
├── packages/
│   ├── domain/                      # 前后端共享类型和校验 schema
│   └── model-manifests/             # 模型能力、参数和计费配置
├── docs/                            # 产品、接口、验收和发布文档
```

## 7. 技术栈如何落地

### 5.1 前端

- React 19：页面和节点组件。
- TypeScript 6：所有跨模块数据使用显式类型。
- Vite 8：开发服务器和生产构建。
- React Flow 12：无限画布、节点、边、缩放、视图和小地图。
- Zustand 5：按领域拆分 nodes、projects、ui、tasks、auth 和 settings slices。
- Tailwind CSS 3：深色主题和设计 token。
- Framer Motion：React 组件和交互过渡。
- Motion：轻量布局和状态动效。
- GSAP：画布连接线、生成状态和复杂序列动效。
- IndexedDB：保存未提交的画布草稿、最近项目缓存和生成结果索引；不作为商业数据的唯一存储。
- Vitest：节点数据、Store Action、任务状态和适配器测试。

### 5.2 服务端

服务端必须存在，因为浏览器不能安全保存平台 API Key，也不能把所有模型调用、额度判断和计费逻辑交给用户浏览器。

推荐第一版采用：

- Node.js + TypeScript。
- Fastify 或同等轻量 HTTP 框架。
- PostgreSQL：账号、项目、画布快照、任务、资产元数据、额度和订单。
- Redis：任务队列、限流、幂等锁和短期状态。
- S3 兼容对象存储：图片、视频、音频和缩略图。
- WebSocket 或 SSE：把生成任务状态推送给前端。
- 独立 Provider Adapter：每个模型厂商单独封装请求、轮询、取消、结果解析和错误分类。

具体供应商可以在真正开工前根据你的 API 平台、部署预算和支付地区确定；在没有确认前，不把某一家云服务写死到代码里。

## 8. 最重要的安全边界

### 6.1 API Key 不能放在前端

前端只发送：

- providerId
- modelId
- 生成参数
- 输入素材的资产 ID
- 当前项目 ID

服务端负责：

- 读取密钥。
- 校验用户是否有权使用该模型。
- 检查余额、套餐和单次额度。
- 调用厂商 API。
- 隐藏厂商密钥、原始请求头和内部错误。
- 保存任务状态和结果。

如果你的第一阶段是“用户自带 API Key”，也仍然建议通过服务端加密保存。日志、消息、项目 JSON、前端 Store 和错误提示中都不能出现完整密钥。

### 6.2 生成任务必须可恢复

每次生成都建立任务记录：

```text
queued → running → succeeded
                   ├→ failed
                   ├→ cancelled
                   └→ expired
```

任务至少包含：用户、项目、节点、provider、model、参数摘要、状态、计费状态、结果资产和错误分类。用户刷新页面后，前端根据任务 ID重新同步，而不是假设浏览器一直在线。

### 6.3 用户数据隔离

每张项目、任务、资产和订单表都必须带 `user_id`。服务端每次读取和写入都进行用户归属校验，不能只依赖前端传入的项目 ID。

## 12. 现在的正式起点

正式起点不是先写模型接口，而是先建立“能长期迭代的独立 Web 项目”并完成阶段 0 和阶段 1。

第一轮实施顺序固定为：

```text
确认独立项目目录
→ 建立 React/Vite/TypeScript 基础工程
→ 接入 React Flow 和 Zustand
→ 做出可操作的无限画布
→ 加入文本/图片/上传节点外壳
→ 加入 Disy 深色/浅色主题
→ 你体验并确认交互
→ 接入真实图片 API
→ 先完成文生图，再完成图生图
```

这样做的原因是：画布交互一旦确定，后面的 API、任务、资产和计费都围绕稳定的节点数据模型建设；如果一开始先接模型，后面很容易因为节点结构和任务状态不稳定而反复重写。
